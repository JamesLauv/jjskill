# 客户资料 → Demo测试框架

从客户提供的业务文档中提取业务规则，生成完整的智能客服Demo测试框架：测试脚本、流程图、对话模拟、技术节点标注。

## 适用场景

当用户拿到客户提供的业务资料（系统操作手册、流程图、培训PPT、政策文档等），需要为AI智能客服Demo准备测试内容时使用本skill。

典型输入：客户的PPT培训材料、操作流程文档、业务规则说明、流程截图。
典型输出：测试用例矩阵、退货/问答场景对话脚本、业务流程图（含技术节点标注）、WEB端对话窗口模拟、对话内容技术备注表。

## 核心工作流

### Phase 1: 读取客户资料，提取业务事实

逐个读取客户文件夹中的所有文档。不同格式用不同方式读取：

- **PPT**：用 `python-pptx` 提取幻灯片文字内容（注意编码，Windows环境用 `sys.stdout.reconfigure(encoding='utf-8')`）
- **Docx**：用 `python-docx` 提取段落和表格
- **PNG/JPG**：直接用 Read 工具查看图片内容
- **MP4**：跳过，记录文件名供后续参考

提取后按以下结构整理：

| 层级 | 内容 |
|---|---|
| 客户是谁 | 公司名称、行业、使用什么系统、覆盖哪些客户类型 |
| 现有系统功能 | 系统模块、核心流程、角色分工 |
| 业务场景全景 | 所有业务分支（如退货原因分类、客户类型差异） |
| 关键规则 | 权限差异、额度管控、审批流、状态判断逻辑 |
| 利益相关方 | 涉及哪些角色（门店、销售、物流、客服等） |

**区分"原文事实"和"推断"**。原文明确写到的规则直接提取；需要推断的标注为"待确认"。

### Phase 2: 与用户交互，补充关键判断

读完资料后先输出结构化分析摘要，然后确认几个关键问题：

1. **交互形态**：Demo是Web端聊天窗、小程序H5、还是独立页面？
2. **数据来源**：用模拟数据还是对接真实API？
3. **场景优先级**：哪些场景是核心（如退货+问答），哪些简单带过？
4. **输出格式**：需要哪些交付物（Markdown/HTML/Excel）？

如果用户已经明确说明，直接进入Phase 3不再追问。

### Phase 3: 生成交付物

根据用户确认的格式和优先级，生成以下交付物（全部或部分）：

#### 交付物1: 测试脚本 Markdown

文件名格式：`[项目名]智能客服Demo-测试脚本与验证框架[-cc].md`

结构：
```
一、测试目标
二、测试场景全景（优先级矩阵表）
三、核心场景测试用例
  - 按客户类型分组（直营/非直营/电商）
  - 按退货方式分组（当场/事前/事后/客情）
  - 每个用例包含：用例ID、用户输入示例、期望意图识别、期望客服行为、判断规则、通过标准
四、知识问答测试用例
  - 产品知识、政策问答、操作指南
五、对话链路测试
  - 多轮对话能力、意图识别边界
六、判断规则矩阵
  - 客户类型×退货权限
  - 订单状态×可选退货方式
  - 退货原因×必填项
  - 发票状态×客户类型
七、边界与异常测试
八、Demo演示脚本（推荐演示流程和时间分配）
附录：关键术语
```

#### 交付物2: 退货流程图 HTML

文件名格式：`[项目名]智能客服-退货流程图与技术节点[-cc].html`

技术规格：
- 单文件HTML，Tailwind CSS CDN
- Tab切换：全景流程图 / 直营客户详细流程 / 非直营客户详细流程
- 每个节点标注颜色：
  - 🔴 红色 = Demo交互节点
  - 🔵 蓝色 = 查询接口（API）
  - 🟢 绿色 = 知识库（KB）
  - 🟡 黄色 = 判断规则（Rules）
  - 🟣 紫色 = UI交互/表单
- 底部汇总所有技术节点，说明正式上线时的实现方式

#### 交付物3: 对话窗口模拟 HTML

文件名格式：`[项目名]智能客服-对话窗口模拟[-cc].html`

技术规格：
- 模拟真实WEB端聊天窗口样式（蓝色头部、聊天气泡、输入框）
- 左侧场景选择面板（3-5个核心场景）
- 右侧对话区：用户蓝色气泡 + 机器人灰色气泡
- 每条机器人回复下方有灰色小字技术注释（标注API/KB/Rules）
- 支持点击切换场景、输入框交互
- 场景覆盖：核心退货场景 + 知识问答 + 边界能力（情绪/模糊意图）

#### 交付物4: 对话内容+技术备注 Excel

文件名格式：`[项目名]智能客服-对话内容与技术备注[-cc].xlsx`

工作表结构：
- 每个演示场景一个工作表（场景一、场景二...）
- 列：序号 | 发言方 | 对话内容 | 技术实现类型 | 技术实现说明 | 正式上线时调用方式
- 发言方按颜色区分：用户蓝色底、客服灰色底
- 技术类型按颜色区分：API蓝色、KB绿色、Rules黄色、UI紫色
- 最后一个工作表：技术节点汇总（所有API/KB/Rules/UI节点清单）

#### 交付物5: 测试用例跟踪表 Excel

文件名格式：`[项目名]智能客服Demo-测试用例跟踪表[-cc].xlsx`

工作表结构：
- 退货场景用例（20+条）
- 知识问答用例（13+条）
- 多轮对话与边界（18+条）
- 测试汇总（按场景分类的通过率统计）
- 测试状态列用数据验证下拉：待测试/测试中/通过/失败/阻塞
- 冻结首行

## 技术节点标注规则

在流程图和对话模拟中，每个交互节点需要标注其技术实现类型：

| 类型 | 标记 | 说明 | 正式上线实现方式 |
|---|---|---|---|
| 接口(API) | 蓝色 | 需要调用外部系统数据 | REST API调用对应微服务 |
| 知识库(KB) | 绿色 | 基于知识库检索或模型推理 | 向量数据库+RAG / NLP模型 |
| 判断规则(Rules) | 黄色 | 业务逻辑判断和分支 | 规则引擎（条件分支） |
| UI交互 | 紫色 | 前端表单和交互组件 | 前端组件 |

常见技术节点映射：
- 客户类型识别 → API（客户信息系统）+ Rules（类型判断）
- 订单状态查询 → API（订单系统）
- 额度查询 → API（额度系统）
- 退货原因匹配 → Rules（原因分类引擎）
- 意图识别 → KB（NLP意图模型）
- 情绪处理 → KB（情绪识别模型+话术库）
- 照片上传 → API（OSS直传）
- 审批流 → API（工作流引擎）+ Rules（按角色不同审批路径）

## 文件输出规则

- 保存到用户指定目录（通常是客户项目文件夹下）
- 文件名加 `[-cc]` 标记表明是Claude Code输出
- 用Python生成Excel时，先写临时 `.py` 文件再执行（避免bash单引号编码问题）
- Windows环境Python脚本开头加 `sys.stdout.reconfigure(encoding='utf-8')`
- Excel用 `openpyxl` 库，需要先检查是否已安装
- HTML文件可直接双击浏览器打开验证

## 与其他jjskill的关系

本skill由 `jjskill` 路由Skill分发，专注于"客户资料→Demo测试框架"这个特定场景。当用户的需求是更广泛的决策材料（方案评估、会议推进、内部评审）时，由 `jjskill` 路由到 `jjskill-doc-to-decision-artifacts`。

区分：
- 本skill：输出测试脚本、对话模拟、流程图标注 → 面向**Demo制作和测试验证**
- jjskill-doc-to-decision-artifacts：输出方案对比、决策矩阵、沟通材料 → 面向**方案评审和推进决策**
